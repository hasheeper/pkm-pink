# PKM PINK 重构需求稿（简版）

## 0. 背景

当前 PKM PINK 项目经历多轮需求膨胀，代码和资源分散在多个 GitPage / 脚本 / 前端页面中，存在以下问题：

1. **ERA 变量结构旧且松散**
   当前存档依赖 ERA，变量结构分散，不利于后续维护、迁移和调试。

2. **Main 版与 Universal 版重复维护**
   常规 Main 版和 Universal 通用版各自拥有状态栏、中间件、前端资源，存在大量重复逻辑。

3. **战斗引擎与前端 / 酒馆脚本耦合较重**
   通用战斗引擎应当被 Main / Universal 共用，但目前版本管理、引用关系和发布路径不够统一。

4. **酒馆助手通讯逻辑重复且脆弱**
   变量读写、Prompt 注入、AI 回复标签解析、iframe 通讯、Dashboard 刷新等逻辑分散在不同脚本中，维护成本高。

5. **需要向 MVU 版本迁移**
   PKM PINK 计划从 ERA 版本重构为 MVU 版本，需要重新整理状态结构、迁移逻辑和中间件读写方式。

---

# 1. 总体目标

将 PKM PINK 重构为：

> **一套统一内核 + 两套内容包 + 一个通用战斗引擎 + 一个酒馆助手桥接脚本。**

目标结构：

```text
PKM PINK Monorepo
├── 通用战斗引擎
├── MVU 状态层
├── 酒馆助手桥接层 pkm-st-bridge
├── Dashboard 通用组件
├── Main 内容包
├── Universal 内容包
├── Main GitPage 前端
└── Universal GitPage 前端
```

核心原则：

- 不再维护两套重复代码；
- Main 和 Universal 只作为不同内容包 / 配置包存在；
- 战斗引擎只保留一份；
- 酒馆通讯逻辑统一由 `pkm-st-bridge` 管理；
- 存档从 ERA 迁移到 MVU；
- 为未来迁移 TavernHeadless 或其他后端预留接口。

---

# 2. 重构重点一：`pkm-st-bridge`

## 2.1 定位

`pkm-st-bridge` 是 PKM PINK 在 SillyTavern / 酒馆助手环境下的统一桥接层。

它不负责战斗规则，不负责宝可梦数值计算，也不负责剧情内容。

它负责：

> **把酒馆助手、MVU 状态、LLM Prompt、AI 回复、Dashboard 前端连接起来。**

---

## 2.2 核心职责

### 2.2.1 MVU 状态读写

`pkm-st-bridge` 需要提供统一状态 API：

```js
PkmBridge.state.load()
PkmBridge.state.save(nextState)
PkmBridge.state.patch(patcher)
PkmBridge.state.backup()
PkmBridge.state.validate()
```

功能要求：

- 从酒馆助手 / MVU 读取当前 PKM 状态；
- 写回修改后的 PKM 状态；
- 写入前进行 schema 校验；
- 写入失败时保留备份；
- 支持 Main / Universal 不同命名空间；
- 避免不同模块直接手写变量路径。

---

### 2.2.2 Prompt 注入

桥接层负责统一管理生成前注入内容。

需要支持：

- 队伍状态注入；
- 当前地图 / 位置注入；
- 天气 / 环境注入；
- NPC / 好感度注入；
- 战斗摘要注入；
- Main 版专属世界观注入；
- Universal 版轻量上下文注入。

推荐接口：

```js
PkmBridge.prompt.registerProvider({
  id: 'party',
  priority: 10,
  build(ctx) {
    return '...'
  }
})
```

要求：

- Prompt block 有顺序；
- 不同模块可独立注册；
- Main / Universal 可启用不同 provider；
- 注入内容需要带命名空间，避免与其他卡冲突。

---

### 2.2.3 AI 回复标签解析

统一解析 AI 回复中的结构化标签，例如：

```xml
<PKM_BATTLE>{...}</PKM_BATTLE>
<PKM_FRONTEND>{...}</PKM_FRONTEND>
<PKM_UPDATE>{...}</PKM_UPDATE>
```

桥接层需要提供：

```js
PkmBridge.artifact.parse(text, tag, schema)
```

功能要求：

- 提取指定 XML 标签；
- 自动去除 markdown code block；
- 宽容处理 JSON 格式问题；
- schema 校验；
- 解析失败时输出错误日志；
- 防止同一条消息重复解析；
- 不覆盖酒馆助手 / MVU 的正常写入逻辑。

---

### 2.2.4 Dashboard / iframe 通讯

统一管理 PKM 前端页面与酒馆之间的通讯。

桥接层负责：

- 创建 iframe；
- 创建状态栏 / 悬浮入口；
- iframe ready 握手；
- 向前端发送初始状态；
- 状态变化后刷新前端；
- 接收前端 action；
- 切换聊天 / 页面卸载时清理监听器；
- 防止重复注入多个 iframe。

通信协议示例：

```js
{
  type: 'PKM_READY',
  product: 'main'
}
```

```js
{
  type: 'PKM_STATE_PUSH',
  payload: {}
}
```

```js
{
  type: 'PKM_ACTION',
  action: 'party.setLead',
  payload: {
    slot: 2
  }
}
```

---

### 2.2.5 前端 Action 分发

Dashboard 不再直接生成变量修改文本，而是发送 action。

例如：

```js
{
  action: 'party.setLead',
  payload: { slot: 3 }
}
```

桥接层接收后：

1. 读取当前 MVU 状态；
2. 调用对应 action handler；
3. 生成 nextState；
4. 校验；
5. 写回 MVU；
6. 通知前端刷新。

需要支持的基础 action：

| Action | 说明 |
|---|---|
| `party.setLead` | 设置先发 |
| `party.updateMove` | 调整招式 |
| `box.deposit` | 放入盒子 |
| `box.withdraw` | 从盒子取出 |
| `box.swap` | 队伍 / 盒子交换 |
| `map.move` | 地图移动 |
| `settings.update` | 修改设置 |
| `battle.launch` | 发起战斗 |
| `battle.applyResult` | 应用战斗结果 |

---

### 2.2.6 Main / Universal Profile 管理

`pkm-st-bridge` 需要支持不同产品配置。

示例：

```js
PkmBridge.init({
  product: 'main',
  stateNamespace: 'pkm_main',
  contentPack: 'main',
  dashboardUrl: 'https://xxx.github.io/pkm-pink/main/'
})
```

```js
PkmBridge.init({
  product: 'universal',
  stateNamespace: 'pkm_universal',
  contentPack: 'universal',
  dashboardUrl: 'https://xxx.github.io/pkm-pink/universal/'
})
```

Main 和 Universal 的差异通过 profile 控制。

---

## 2.3 `pkm-st-bridge` 不负责什么

明确不做：

- 不实现宝可梦伤害公式；
- 不实现战斗引擎；
- 不硬编码 Main 世界观；
- 不维护 NPC 剧情内容；
- 不重写酒馆助手；
- 不重写 MVU 底层；
- 不把 Main 和 Universal 业务强行合并。

# 3. 重构重点二：ERA → MVU 化

## 3.1 目标

将旧 ERA 存档结构迁移为统一 MVU 状态结构。

目标是让业务代码不再依赖 ERA，而是统一读写：

```js
pkmState
```

---

## 3.2 新 MVU 状态结构草案

建议新状态集中在一个顶层对象下：

```json
{
  "pkm": {
    "meta": {},
    "player": {},
    "party": {},
    "box": {},
    "world": {},
    "npcs": {},
    "battle": {},
    "settings": {},
    "runtime": {}
  }
}
```

---

## 3.3 字段说明

### `meta`

存放版本与产品信息。

```json
{
  "schemaVersion": 1,
  "product": "main",
  "contentVersion": "0.1.0",
  "createdAt": "",
  "updatedAt": ""
}
```

---

### `player`

玩家信息与机制解锁。

```json
{
  "name": "{{user}}",
  "trainerProficiency": 0,
  "unlocks": {},
  "bonds": {}
}
```

---

### `party`

当前队伍。

```json
{
  "slots": [],
  "transferBuffer": null
}
```

要求：

- 最多 6 个正式槽位；
- 支持第 7 只临时缓冲；
- 每只宝可梦包含 species、nickname、level、moves、item、ability、AVS、mechanic 等信息。

---

### `box`

PC 盒子。

```json
{
  "boxes": [],
  "indexes": {}
}
```

要求：

- 支持队伍与盒子互转；
- 支持多选；
- 支持盒子容量扩展；
- 支持 Main / Universal 共用结构。

---

### `world`

世界状态。

```json
{
  "location": {},
  "time": {},
  "weatherGrid": {},
  "pokemonSpawns": {},
  "phenomenon": {}
}
```

Main 版可使用完整地图、天气、刷新系统。
Universal 版可以只使用最小字段。

---

### `npcs`

NPC 好感与阶段。

```json
{
  "records": {}
}
```

Main 版包含固定 NPC。
Universal 版可为空或由用户自定义。

---

### `battle`

战斗临时状态与最近结果。

```json
{
  "lastConfig": null,
  "lastResult": null,
  "pendingNarrative": null
}
```

原则：

- 战斗引擎输出结果可以暂存；
- 不建议把大量运行时过程长期塞进存档；
- 可清理、可重算的内容放 runtime。

---

### `settings`

系统设置。

```json
{
  "enableAVS": true,
  "enableCommander": true,
  "enableEVO": true,
  "enableBGM": true,
  "enableSFX": true,
  "enableClash": false,
  "enableBattleEnvironment": true
}
```

---

### `runtime`

临时缓存。

```json
{
  "caches": {},
  "flags": {},
  "migration": {}
}
```

用于：

- 迁移记录；
- 临时 UI 状态；
- 最近刷新缓存；
- 防重复处理标记。

---

# 4. ERA → MVU 迁移器

## 4.1 迁移目标

提供旧存档迁移能力，不要求用户全部重开档。

迁移入口：

```js
PkmBridge.migration.fromEra()
```

或开发脚本：

```bash
pnpm migrate:era-to-mvu
```

---

## 4.2 需要迁移的数据

| 旧 ERA 数据 | 新 MVU 位置 |
|---|---|
| 玩家名 | `pkm.player.name` |
| 熟练度 | `pkm.player.trainerProficiency` |
| 机制解锁 | `pkm.player.unlocks` |
| 羁绊道具 | `pkm.player.bonds` |
| 队伍 slot1-6 | `pkm.party.slots` |
| transfer_buffer / slot7 | `pkm.party.transferBuffer` |
| PC 盒子 | `pkm.box` |
| 位置 | `pkm.world.location` |
| 时间 | `pkm.world.time` |
| 异变 | `pkm.world.phenomenon` |
| 天气缓存 | `pkm.world.weatherGrid`，可选 |
| 刷新缓存 | `pkm.world.pokemonSpawns`，可选 |
| NPC 好感 | `pkm.npcs.records` |
| 设置项 | `pkm.settings` |

---

## 4.3 可以不迁移 / 可重算的数据

以下数据可丢弃或重算：

- 战斗中间态；
- 临时按钮状态；
- Dashboard 展开状态；
- 临时 prompt flags；
- 过期野生刷新缓存；
- 过期天气缓存；
- 旧日志缓存。

---

## 4.4 迁移安全要求

迁移时必须：

1. 先备份旧 ERA 数据；
2. 转换为新 MVU；
3. 执行 schema 校验；
4. 校验通过后写入；
5. 写入失败则保留旧数据；
6. 在 `runtime.migration` 中记录迁移信息。

示例：

```json
{
  "migration": {
    "from": "ERA",
    "to": "MVU",
    "migratedAt": "2026-xx-xx",
    "eraBackupExists": true
  }
}
```

# 5. Main / Universal 处理方案

## 5.1 不再维护两套核心代码

Main 和 Universal 不应该分别维护：

- 战斗引擎；
- 状态读写；
- 酒馆通讯；
- Dashboard 基础组件；
- 宝可梦队伍 / 盒子逻辑；
- AI 标签解析。

这些全部共用。

---

## 5.2 用 Profile 区分版本

Main：

```js
{
  product: 'main',
  contentPack: 'main',
  enabledModules: [
    'party',
    'box',
    'map',
    'battle',
    'npc',
    'relationship',
    'weather',
    'transit',
    'story'
  ]
}
```

Universal：

```js
{
  product: 'universal',
  contentPack: 'universal',
  enabledModules: [
    'party',
    'box',
    'battle',
    'settings'
  ]
}
```

---

## 5.3 内容包拆分

```text
content/
├── main/
│   ├── npcs/
│   ├── maps/
│   ├── story/
│   ├── unlocks/
│   └── prompts/
│
└── universal/
    ├── presets/
    ├── prompts/
    └── default-state.json
```

Main 保留完整世界观。
Universal 只保留通用宝可梦框架。

# 7. 分阶段实施计划

## 阶段 1：统一仓库

目标：

- 把现有 GitPage、战斗引擎、状态栏、中间件文件收进一个 monorepo；
- 保持功能不变；
- 修正路径；
- 建立统一构建脚本。

验收：

- Main 页面能构建；
- Universal 页面能构建；
- 战斗 demo 能运行；
- 旧功能不明显退化。

---

## 阶段 2：抽通用战斗引擎

目标：

- 战斗引擎独立为 `packages/battle-engine`；
- Main / Universal 共用同一引擎；
- 移除重复引擎代码。

验收：

- 普通战斗可运行；
- Mega / Z / 极巨 / 太晶基本可用；
- AVS / Clash / 天气不因路径迁移失效。

---

## 阶段 3：设计并实现 MVU 状态层

目标：

- 新 MVU schema 定版；
- 实现 `pkm-state-mvu`；
- 实现 normalize / validate / patch；
- 写 ERA → MVU 迁移器。

验收：

- 新开档生成 MVU 状态；
- 旧 ERA 数据可迁移；
- 迁移后 party / box / unlocks / location / npc love 可保留；
- 校验失败不会污染存档。

---

## 阶段 4：实现 `pkm-st-bridge`

目标：

- 统一酒馆助手读写；
- 统一 AI 标签解析；
- 统一 iframe 通讯；
- 统一 action 分发。

验收：

- Dashboard 能从 MVU 获取状态；
- 前端 action 能写回 MVU；
- AI 回复中的 `<PKM_BATTLE>` 能解析；
- Main / Universal 可通过 profile 切换。

---

## 阶段 5：内容包化

目标：

- Main 内容迁入 `content/main`；
- Universal 内容迁入 `content/universal`；
- Dashboard / Bridge 按 profile 加载内容包。

验收：

- Main 保持完整世界观功能；
- Universal 不加载 Main 专属剧情 / 地图锁；
- 两者共用战斗引擎和桥接层。

---

# 8. 验收标准总表

| 模块 | 验收标准 |
|---|---|
| Monorepo | 所有分散文件纳入统一仓库 |
| 战斗引擎 | 只保留一份，被 Main / Universal 共用 |
| MVU 状态 | 新开档和旧档迁移都可用 |
| ERA 迁移 | 迁移失败可回滚 |
| pkm-st-bridge | 统一变量、Prompt、标签、iframe、action |
| Main 版 | 完整世界观功能保留 |
| Universal 版 | 轻量通用框架可独立运行 |
| GitPage | 同仓库多路径发布 |
| Debug | 能导出当前状态和最近错误 |

---

# 9. 非目标

本轮重构不做：

- 不重写完整战斗系统；
- 不新增大量剧情；
- 不扩展新世代机制；
- 不重新设计全部 UI；
- 不立即迁移 TavernHeadless；
- 不把 Main 和 Universal 合并成一个内容；
- 不继续扩展 ERA 结构。

---

# 10. 简短总结

本轮重构的核心不是“加功能”，而是“收束工程结构”。

重点有两个：

1. **ERA → MVU 化**
   把旧存档迁移为统一、可校验、可版本管理的 MVU 状态。

2. **实现 `pkm-st-bridge`**
   把酒馆助手相关的变量读写、Prompt 注入、AI 标签解析、Dashboard 通讯、前端 action 分发统一管理。

最终目标：

> **一套 PKM 内核，两套内容包，一个通用战斗引擎，一个统一酒馆桥接脚本。**
